**Three server realities the UI had to be built around, not around-talked:**

1. **`Email/queryChanges` always throws `cannotCalculateChanges`** and
   `Email/query` advertises `canCalculateChanges: false`. `arch.md` §4 planned
   the thread list on `queryChanges`; that plan is not available. The store uses
   RFC 8620 §5.6's **re-query fallback** — still one round trip (query +
   back-referenced get), bounded by `REFRESH_CAP` so a push cannot re-read an
   unbounded list. A test asserts the store never emits `Email/queryChanges`,
   against a fake that throws exactly as the server does.
2. **Server search does not cover message bodies.** The `text` condition is a
   LIKE over `subject`/`preview`/`from_json`/`to_json` (FTS unwired —
   `common/004`). The UI says so in `SEARCH_SCOPE_NOTE` under the search box and
   in `describeSearchScope` under the results, and a test proves a body-only word
   really is missed rather than merely warning about it in the abstract.
3. **`Email/set create` has no attachment path.** Forwarding therefore drops
   attachments; `buildForwardDraft` returns `droppedAttachments` and the composer
   warns. Wiring the real path is T3.

**Verified by driving the built app** in headless Chrome, not only by tests:
mailbox list + unread counts, thread grouping, thread open, blocked tracking
pixel → "Show images", `j`/`k`/`?`/`e` keyboard triage (Inbox badge 3 → 1),
search returning 0 for a body-only word, composer opening with Send disabled
until valid.

That drive caught a bug **no test and no clean build could see**: a hand-written
`script-src 'self'` meta CSP blocked Astro's inline hydration bootstrap, so the
island never mounted and the page rendered an empty body — while `astro build`
and all 245 tests reported success. CSP is now generated by Astro
(`security.csp` in `astro.config.mjs`, per-build script hashes), with
`frame-ancestors` and the header-only protections in `webmail/public/_headers`.

### Rough edges (T2 is greenfield UI)

- **Threading is window-local.** `Email/query` has no `collapseThreads`, so rows
  are grouped over the emails loaded so far; a thread's older message on an
  unfetched page is not counted until you scroll to it.
- **Re-saving a draft is create + destroy**, because a stored message is a
  pointer at an immutable blob. That charges the `delete` scope, so a
  `draft`-but-not-`delete` token accumulates copies. `replaces` is optional.
- **Sending is two round trips.** Back-references only replace top-level args, and
  `submitOne` does not resolve `#creationId`, so the draft must exist before the
  submission can name it.
- `sentAt` is `null` for every message server-side; the UI sorts and displays on
  `receivedAt`.
- Move-to-folder uses `window.prompt` — functional, not a picker.
- `scopesForPatch` MIRRORS the server's `requiredScopesForEmailSet`; it predicts
  refusals for greying out actions, and can drift.
- No attachment upload/download UI yet (T3), no folder-management UI
  (`Mailbox/set` exists), no undo, no drag-and-drop, no mobile pane routing.

## T2 — Mail surfaces ✅

- Mailbox list · virtualized thread list · thread view (sanitized HTML, quote collapsing,
  remote content blocked) · compose/reply/forward with drafts · server-side search.
- Keyboard-first triage (archive/label/next without the mouse).

**Done when:** a full day of real mail is workable in it; a thread open is one batched

**Met.** A thread open is one request (`Thread/get` + back-referenced `Email/get`),
asserted in `threadView.test.ts`. The sanitizer has 48 adversarial tests —
`<script>` (including `</script >` smuggling), every `on*` handler, `javascript:`
behind decimal/hex entities and control characters, `svg`/`math`/`iframe`/`base`,
`data:text/html`, CSS `expression()`/`url()`/`position:fixed`, DOM-clobbering
`id`/`class`, and remote-image blocking with a per-message opt-in.

## T4 — Capability gating + plain-client proof

- The `urn:bullmoose:agent` gate helper, applied at every future-agent seam.
- A test (and a manual run) against a session **without** the agent capability.

**Done when:** with the capability absent, nothing errors, 400s, or renders a dead

## Verification

Per `.claude` project practice: drive the real app, don't just pass tests. A green run
here means *opening it and doing a day of mail*, including a large attachment send and a
Files round trip.

## Risk

**This is the largest slice.** A mail UI is a lot of surface — virtualization, HTML
rendering, compose semantics, sync reconciliation. Two mitigations: (1) the JMAP client
module is the only piece that must be right early, since everything else is replaceable
UI; (2) ship T1+T2 as a usable read/reply client before polishing.
